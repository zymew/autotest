# 第一阶段实施操作指南（沙盒主链路版）

## 1. 角色划分

### 控制机：Ubuntu Desktop

- `dnsmasq`：给 DUT 分配 PXE 地址并通过 TFTP 交付 `ipxe.efi`
- `nginx`：提供 `wimboot`、`boot.wim`、规格库文件
- Python 接收服务：接收 DUT 回传的汇总结果 JSON
- 规格标准库：集中维护各机型三大件匹配规则

### 开发机：Windows

- 制作 WinPE
- 编译 `ipxe.efi`
- 调试 Python Agent
- 准备 BurnInTest 便携版和各机型 `.bitcfg`

### DUT：被测工控机

- 通电后从 PXE 进入 WinPE
- 自动运行 Agent
- 读取三大件信息
- 判断是否进入 BurnInTest
- 回传结果 JSON

## 2. 控制机目录建议

```text

│   └── app.py
```

## 5. Agent 运行流程

1. 初始化时间戳与输出目录
2. 读取 BIOS / BaseBoard / ComputerSystem / DiskDrive / MemoryChip 等信息
3. 用本地识别规则归一出 `model_code`
4. 从控制机下载规格库
5. 读取 CPU / 内存 / 硬盘实际信息
6. 判定基础健康状态
7. 输出 `hardware_check_{sn}.json`
8. 若规格不匹配，直接写 `final_result_{sn}.json` 并回传
9. 若规格匹配，按 `burnin_profile` 启动 BurnInTest
10. 输出 `final_result_{sn}.json` 并回传控制机

## 6. 规格不匹配处理

- 任何一项三大件不匹配，整体判 `FAIL`
- 不进入 BurnInTest
- `failure_reason` 写明不匹配项
- 仍然必须回传最终结果 JSON

## 7. BurnInTest 准备规则

- 每个机型单独准备 `.bitcfg`
- `.bitcfg` 必须通过 GUI 预配置后导出
- 串口不能只保留 `COM1`
- 每个机型需将全部目标串口写入对应配置
- 负载目标：
  - CPU 100%
  - RAM 100%
  - GPU 相关项 100%
  - Network 100%
  - Com Port(s) 加入全部目标串口

详细规范见 [docs/BurnInTest配置准备规范.md](/C:/Users/19306/Documents/自动测试/docs/BurnInTest配置准备规范.md)。

## 8. 沙盒验收步骤

### 用例 A：规格匹配

- 启动控制机全部服务
- 给 DUT 通电
- 确认 DUT 自动进入 WinPE 并启动 Agent
- 确认 `hardware_check_{sn}.json` 生成
- 确认 DUT 自动进入对应 BurnInTest 配置
- 确认控制机收到 `final_result_{sn}.json`

### 用例 B：规格不匹配

- 修改控制机规格库，使某项与 DUT 实际配置不符
- DUT 通电后应完成识别与比对
- Agent 应阻断 BurnInTest
- `overall_result` 为 `FAIL`
- 控制机仍应收到最终结果 JSON

### 用例 C：结果接收异常

- 暂停控制机结果接收服务
- DUT 完成流程后应明确记录结果回传失败
- 不允许静默显示成功
